## Jobs stuck WAITING in the docker compose stack

**Context.** Brought up the stack with `--profile cueweb`. Jobs submitted with the
test scripts in `~/temp/OpenCue_tests` showed in CueWeb but never ran: every frame
stayed WAITING, and frame 0001 showed `exit=299` (Cuebot's "frame cleared" code).

**Root cause.** Cuebot's log on every dispatch attempt:

```
ABORTED: Not launching, user nyue(1000:0) could not be created.
  × Failed to create user nyue: useradd: UID 1000 is not unique
```

- RQD looks up the job owner **by name** and, if the name is missing, runs
  `useradd --uid <uid>` (`rust/crates/rqd/src/system/linux.rs`,
  `create_user_if_unexisting`).
- `rust/Dockerfile.rqd` created a `rqd` user with UID 1000, which is also the
  usual first user on a Linux host (me).
- `useradd` failed, Cuebot unbooked the frame ("accounting error"), and the frame
  went back to WAITING, forever.

Confirmed by adding a non-unique `nyue` alias by hand inside the running container:
all 10 frames then succeeded.

**Decision: fix both sides** (commit `59f1f128`).

- *RQD:* if the UID already exists under another name, pass `--non-unique` to
  `useradd`. Frames run under the numeric UID anyway, so this handles any clash,
  not just this image's. Logs when it does so.
- *Image:* create `rqd` with `useradd -r` (system UID, now 999) so it no longer
  occupies UID 1000.

Why both: the image fix alone only moves the problem (any submitter whose UID
matches a user baked into the image would still fail); the RQD fix alone would
leave job owners aliased onto `rqd`.

Tested by recreating the container and forcing a clash with a placeholder
`blocker` user on UID 1000: RQD logged the alias and the job ran 10/10.

## Job owner created with root as primary group

**Context.** The error above also showed `nyue(1000:0)`: the account was created
with GID 0 (root).

**Cause.** Cuebot never sets `RunFrame.gid` (only `uid`, in
`DispatchSupportService.java`), so it arrives as the protobuf default 0. RQD
treated that inconsistently:

- `running_frame.rs` maps `gid <= 0` to `runner.default_gid` (20) for the frame
  process ("protection against frames that want to become root").
- `frame/manager.rs` passed the raw 0 to `useradd`, so the account's primary
  group was root.

Python RQD didn't have this bug: it omits `-g` when gid is 0.

Impact is small in the compose stack (`run_as_user` is off there). On a real farm
with `run_as_user: true`, anything that logs in as the artist through the
normal account lookup (`su`, `sudo -u`, ssh, cron) would get the root group.

**Decision:** apply the same `default_gid` fallback in `manager.rs` before creating
the user, so the account and the frame process agree (commit `9f7903dc`).
Verified: the recreated account is `uid=1000(nyue) gid=20(dialout)`.

Side note: on the Debian RQD image, GID 20 is `dialout`. Odd, but it is already the
group every frame runs as with `run_as_user` on. Changing `default_gid` for the
image is a separate decision, not taken.
